# 项目结构规范

> 本文件覆盖：标准目录结构、模块边界、文件命名与 .gitignore 必须覆盖的范围。
> 给谁用：初始化项目、新建模块/目录、调整目录结构或配置 .gitignore 时加载。

## 核心原则

沿用项目已明确的结构；新项目按实际职责建立模块目录，不为模板补空目录。以下是 C++ 多模块项目示例，不是所有语言或小项目的必备骨架。

---

## 标准目录结构

```
project/
├── src/                        # 源代码
│   ├── core/                   # 核心库（无平台依赖）
│   │   ├── data_structures/    # 通用数据结构
│   │   ├── algorithms/         # 通用算法
│   │   └── utils/              # 工具函数（仅允许存在于 core/ 下）
│   ├── module_a/               # 业务模块 A
│   │   ├── ModuleA.cpp
│   │   ├── ModuleA.h
│   │   ├── ModuleAProtocol.cpp
│   │   └── ModuleAProtocol.h
│   ├── module_b/               # 业务模块 B
│   │   ├── ModuleB.cpp
│   │   ├── ModuleB.h
│   │   ├── ModuleBProtocol.cpp
│   │   └── ModuleBProtocol.h
│   ├── ui/                     # UI 模块
│   │   ├── MainWindow.h
│   │   ├── MainWindow.cpp
│   │   ├── widgets/            # 自定义控件
│   │   └── views/              # 视图组件
│   ├── network/                # 网络模块
│   │   ├── NetworkClient.h
│   │   ├── NetworkClient.cpp
│   │   ├── protocols/          # 协议实现
│   │   └── serializers/        # 序列化/反序列化
│   └── main.cpp                # 入口

├── include/                    # 公共头文件（对外暴露）
│   └── project_name/           # 命名空间对应目录
│       ├── core/
│       ├── module_a/
│       └── module_b/

├── tests/                      # 测试
│   ├── unit/                   # 单元测试
│   │   ├── core/
│   │   ├── module_a/
│   │   └── module_b/
│   ├── integration/            # 集成测试
│   └── fixtures/               # 测试数据

├── docs/                       # 项目知识，内部结构只在 文档规范.md 维护
│   ├── project_intro.md         # 项目介绍：目标、用户、边界、技术栈概览
│   ├── project_context.md       # AI 会话摘要入口（非权威）
│   └── adr/                     # 长期决策

├── scripts/                    # 构建/部署/工具脚本
│   ├── build.sh
│   ├── deploy.sh
│   └── format.sh

├── tools/                      # 项目相关工具
│   └── codegen/

├── third/                      # 第三方库（源码 / header-only 直接集成）
│   └── README.md               # 记录每个库的版本、来源、许可证

├── CMakeLists.txt              # 顶层构建文件
├── .clang-format               # 代码格式化配置
├── .clang-tidy                 # 静态分析配置
├── .gitignore
└── README.md
```

示例中的 UI、network、include、docs 等仅在实际需要时建立；项目根另放 `AGENTS.md` 作为代理入口。文档职责和创建条件只在 `文档规范.md` 维护，不因目录树中出现文件名就创建它。

## 模块目录规范

独立模块默认对应目录与命名空间；单一职责的小程序可先在 src 根组织少量文件，出现真实模块边界后再拆分。

```
module_a/                  # 目录名 = 模块名（snake_case）
├── ModuleA.h              # 模块主类（PascalCase）
├── ModuleA.cpp
├── ModuleAProtocol.h      # 协议/数据结构（PascalCase）
├── ModuleAProtocol.cpp
├── ModuleATypes.h          # 类型定义（枚举、结构体）
└── ModuleAConfig.h         # 配置类
```

禁止：

* 多模块项目的业务文件无边界地混放在 src 根目录
* 一个目录包含多个不相关的模块
* 模块内部的头文件和 .cpp 文件放在不同目录（例外：对外公共头统一放 `include/`）

---

## 分层与依赖方向

已有项目以明确的架构约定为准；新项目可采用以下默认分层，禁止未经设计引入反向或循环依赖：

```text
ui/（入口与展示）→ module_a / module_b（业务模块）→ network/ 等基础设施 → core/（基础库）
```

* `core/` 最底层：不依赖任何其他模块，不含平台、UI 依赖。
* 基础设施模块（`network/` 等）只依赖 `core/`。
* 业务模块依赖基础设施与 `core/`；同层业务模块默认互不依赖，确需协作时经接口、事件，或把共享逻辑下沉。
* `ui/` 只经公共接口使用业务模块；业务模块禁止 include UI 头文件。
* 新增依赖先核对目标依赖图；采用依赖倒置时将抽象放到合适层，区分源码依赖与运行时调用方向，不把默认示例当作唯一架构。

## 文件命名规范

| 类型 | 命名 | 示例 |
| ------ | ------ | ------ |
| 类文件 | PascalCase | `MotionController.h` |
| 工具函数文件 | snake_case | `string_utils.h` |
| 测试文件 | 类名_test | `MotionController_test.cpp` |
| 钩子测试文件 | 类名_hook_test | `MotionController_hook_test.cpp` |
| 协议文件 | 模块名 + Protocol | `MotionProtocol.h` |
| 类型文件 | 模块名 + Types | `MotionTypes.h` |
| 配置类 | 模块名 + Config | `MotionConfig.h` |

## 禁止的目录结构

以下目录结构视为不合格：

```
// 禁止：文件全部散落在 src/
src/
├── aaa.cpp
├── bbb.cpp
├── ccc.h
├── new.cpp          // 不知道是什么
├── new2.cpp         // 更不知道是什么
├── test.cpp         // 不知道测试谁
├── test_new.cpp     // 彻底混乱
├── temp.cpp         // 临时文件没删
└── old_code.cpp     // 废弃代码没删
```

```txt
// 禁止：业务层级出现无意义杂物箱目录（utils 仅允许在 core/ 下）
src/
├── utils/           // 垃圾桶目录（业务层禁止）
├── helpers/         // 另一个垃圾桶
├── common/          // 第三个垃圾桶
└── misc/            // 第四个垃圾桶
```

## 目录扩展原则

新增模块时：

1. 判断是否属于已有模块的扩展 → 放入已有目录
2. 判断是否是新功能模块 → 创建新目录
3. 保持命名一致 → 目录名反映模块职责

禁止在已有模块目录下创建不相关的新文件。

---

## 生成代码

* 生成物统一落在 `src/generated/` 或模块内 `generated/` 子目录，禁止与手写文件混放；生成目录内不得出现手写文件。
* 支持注释的生成文件标注来源与重生成方式；不支持注释时在生成配置或邻近说明中记录。
* 自有生成脚本、模板与配置必须入库，命令由项目根 `AGENTS.md` 指向实际构建或脚本入口；外部生成器须锁定版本与来源。
* 生成物是否入库沿用项目策略，只有真实长期取舍时才需要 ADR：入库时 CI 校验重生成无差异；不入库时由构建自动生成，不能依赖本机残留。
* 禁止只提交生成物不提交生成脚本，也禁止手改生成文件而不改模板。

## Git 忽略规范

`.gitignore` 必须覆盖六类：构建产物（`build/`、`cmake-build-*/`、`*.o/obj/exe/dll/so`）、IDE 临时文件（`.vs/`、`*.user`、`*.suo`）、测试输出（`Testing/`、`coverage/`）、包管理器与第三方构建输出（`vcpkg_installed/`、`third/**/build/`、`third/**/CMakeFiles/`）、临时文件（`*.tmp`、`*.bak`、`*~`）、密钥与本地凭据（`.env`、`*.pem`、`*.key`、`*.p12`）。

直接集成的 `third/` 源码、许可证和版本清单必须纳入版本控制，禁止忽略整个 `third/`。具体忽略项由项目版本化的 `.gitignore` 维护；规则只定义范围，不要求生成工具。
