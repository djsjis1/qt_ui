# 测试规范

> 本文件覆盖：测试框架、目录与命名、必测场景、覆盖率与测试钩子的登记方式。
> 给谁用：编写、修改或运行测试时加载；代码侧钩子写法见 `C++项目规范.md`，构建开关见 `C++构建与依赖规范.md`。

## 测试框架

新项目默认使用 GoogleTest；已有成熟测试框架继续沿用，不为套用模板迁移。具体版本由实际依赖声明或锁文件维护，锁定可复现版本/commit，禁止使用浮动分支或 `latest`。

框架引入与版本治理统一遵循 `C++构建与依赖规范.md`，不在本文件重复维护依赖规则。

禁止：

* 自研测试框架（已有成熟开源方案，不得重复造轮子）
* 用临时 `main` 加 assert 替代应入库的回归测试；临时复现程序可作为诊断证据，但不等于正式测试覆盖

## 测试目录结构

与 `项目结构规范.md` 对齐：

```
tests/
├── unit/                   # 单元测试（按模块镜像 src/ 结构）
│   ├── core/
│   ├── module_a/
│   └── module_b/
├── integration/            # 集成测试
├── fixtures/               # 测试数据文件
└── CMakeLists.txt
```

测试文件命名：`<类名>_test.cpp`（如 `MotionController_test.cpp`）。

依赖测试钩子的用例（验证 UI / 硬件 / 时序等不可自动化路径）放在与常规单测相同的目录，但必须单独成文件，命名为 `<类名>_hook_test.cpp`。

原因：开关关闭时必须能把钩子用例整体排除，而常规单测在任何构建下都要能编译运行；混在同一文件里就无法分别控制。对应关系必须登记在 `docs/test_hooks.md`（见下节）。

## 四类必测场景

| 类别 | 测什么 | 触发条件 |
| ------ | -------- | ---------- |
| 单元测试 | 单个类/单个函数的逻辑 | 所有新增公共逻辑 |
| 集成测试 | 多模块协作、协议收发闭环 | 新增模块或协议 |
| 压力测试 | 高负载下的性能与稳定性 | 性能关键路径 |
| 异常测试 | 边界、非法输入、资源失效 | 所有外部输入路径 |

异常测试至少覆盖：

* 空指针 / 非法参数
* 越界下标、溢出长度
* 网络断开、文件缺失、设备离线
* 并发竞争场景（若涉及多线程）

性能关键路径的变更必须附带可复现的基准对比（命令、环境、前后数据），并在交付结论中引用；不得以主观感受作为性能结论。

## 命名规范

测试用例使用 `被测方法_场景_预期结果` 格式：

```cpp
TEST(DecodeFrameTest, nullPacket_returnsNullopt);
TEST(DecodeFrameTest, validPacket_returnsFrame);
TEST(CommandQueueTest, undoBeyondDepth_keepsInitialState);
```

命名必须表达「在什么输入下，期望什么行为」。

禁止 `test1`、`testXxx` 等无意义命名。

## 测试编写原则

* 一个用例只验证一个行为
* 测试必须独立：无顺序依赖或共享可变状态；只读数据可共享
* Arrange-Act-Assert 结构清晰
* 业务单元测试默认用 fake/mock 隔离外部副作用；集成测试允许受控真实依赖，如临时目录、本地服务或隔离数据库，禁止依赖生产环境与不可控外网
* 禁止先写实现再「凑」出让它通过的测试（先明确预期行为）

---

## 测试稳定性

* 为快速反馈集设定时长预算（小项目可从 30 秒起）；超出时分析热点、分片或标记慢测，不因耗时改变单元/集成分类。
* 用例必须可重复：时间、随机数与资源路径采用可控来源；真实依赖使用隔离实例并负责清理，不共享不受控环境。
* 异步结果优先用完成通知、future 或条件变量加超时等待；只能轮询时设置截止时间与合理间隔，避免忙等。禁止以固定 sleep 后假定完成。
* flaky 用例记录复现证据、负责人、跟进位置和期限；确需隔离时保留可见的独立检查与覆盖缺口，不静默禁用、不靠重跑掩盖，不因期限到期直接删除有效回归覆盖。

---

## 覆盖率要求

* 新增逻辑必须有测试覆盖。无法自动化的路径（UI 点击、硬件依赖、时序敏感）经测试钩子自测，或在交付结论中说明替代验证，不得静默跳过
* 核心模块目标：行覆盖率 ≥ 80%，分支覆盖率 ≥ 60%。项目未配置覆盖率工具时该门槛不生效，但必须在交付结论中写明“未测量”。
* 覆盖率报告纳入 CI 的项目，覆盖率下降必须说明原因

## 测试钩子：清单登记与构建联动

钩子的设计与实现规范见 `C++项目规范.md`「AI 自测钩子」，本节定义钩子与测试体系的衔接。

### 钩子清单：`docs/test_hooks.md`

新增 / 删除钩子时必须同步维护，格式：

```markdown
| 钩子 | 所在类/文件 | 自测用途 | 依赖用例 | 计划剔除时机 |
|------|------------|----------|----------|--------------|
| testHook_triggerUndo | TimelineController | 验证撤销链路（UI 按钮无法自动点击） | TimelineController_hook_test.cpp | UI 自动化接入后 |
```

* 记录钩子的保留或剔除条件；长期测试接口不必强行设删除日期。其他自动化已等效覆盖后再清理，不能一并丢失独有的回归覆盖。
* 剔除时只需关闭构建开关验证主链路不受影响，再删除集中声明的钩子段与对应清单项，无需全局搜索散落代码。

### 构建联动

* 构建配置与开关唯一规则见 `C++构建与依赖规范.md`；钩子源和用例必须使用相同生效条件。
* 钩子关闭时只排除依赖钩子的用例源，不移除整个混合测试目标；常规单测仍执行。
