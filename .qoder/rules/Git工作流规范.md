# Git 工作流规范

> 本文件覆盖：提交格式、分支模型、提交前检查、PR/MR 门禁与 CI 配置治理。
> 给谁用：执行 Git 写操作或修改流水线前加载；授权边界见 `工程总纲.md`，只读检查不要求额外授权。

## 定位与原则

本文件定义版本控制、PR/MR 与 CI 配置变更的协作规则。

- 提交保持原子、可审查、可回滚；不把无关格式化、生成物或临时文件混入变更。
- 受保护分支不直接提交或推送；通过 PR/MR 合入并由平台门禁执行。
- CI 配置视为可执行的高权限代码：最小权限、最小信任范围、可审查变更。
- 本文件定义执行细则，不授予提交、推送或合并权限；授权统一遵循 `工程总纲.md`。

## Commit 格式

使用 `<类型> <描述> (<范围>)`：

```text
新功能 支持移动操作撤销 (timeline)
```

`范围` 为受影响模块、子系统或配置区域；无法准确归属时可省略。`描述` 使用中文，简洁描述完成的动作，不超过 50 字。变更涉及 ADR 时在描述或 PR 正文中注明 `ADR-XXX`。

若仓库启用了 Conventional Commits 系工具链（commitlint、semantic-release 等），使用完整格式 `type(scope): 描述`（scope 可省略），例如 `feat(timeline): 支持移动操作撤销`；不能只替换中文类型而保留原格式。类型及破坏性变更标记遵循仓库配置，同一仓库只用一种风格。

| 类型 | 使用场景 |
| --- | --- |
| `新功能` | 新功能 |
| `修复` | 缺陷修复 |
| `重构` | 不改变外部行为的重构 |
| `性能` | 性能优化 |
| `文档` | 仅文档变更 |
| `测试` | 仅测试变更 |
| `构建` | 构建系统、依赖或工具链变更 |
| `流水线` | CI/CD 配置、GitHub Actions 或流水线脚本变更 |
| `杂务` | 其他不影响产品行为的维护 |
| `回退` | 回滚已有变更 |

规则：

- 一个 commit 对应一个完整逻辑变更，可包含多个相互依赖的文件；禁止按文件机械拆分，也禁止混合不相关职责。
- 禁止 `temp`、`fix bug`、无上下文 `WIP` 等不可追溯信息。
- 默认提交应可构建并通过其适用的验证；纯文档、元数据等不触发构建的变更应在 PR 中说明验证方式。
- 不提交构建产物、临时文件、密钥、访问令牌或本地环境配置。

## 分支与历史

以仓库已配置的分支模型为准。没有项目专属约定时，采用以下默认策略：

| 分支 | 用途 |
| --- | --- |
| `main` | 受保护的发布主线，不直接提交 |
| `develop`（如仓库启用） | 日常集成分支，通过 PR 合入 |
| `功能/<中文描述>` | 功能或重构变更 |
| `修复/<中文描述>` | 缺陷修复 |
| `发布/vX.Y.Z`（如仓库启用） | 发布准备，仅接受发布阻塞问题修复 |

功能分支命名 `功能/中文描述`、修复分支 `修复/中文描述`，简短可读即可。中文分支须确认 CI 与跨平台工具支持；未确认时使用 ASCII 名称（如 `feat/short-desc`）。显示转义不等于分支编码错误，不为改善显示擅自修改 Git 配置。开始操作前检查当前分支和已有工作，避免覆盖他人修改或重复建分支。

禁止对已推送的共享历史执行 rebase、reset 或 force push，除非用户明确授权且仓库策略允许。需要整理未推送的个人分支历史时，先确认没有协作者依赖该分支。

## 提交前检查

在用户授权提交后，按实际变更执行：

1. 查看 `git status`，确认变更范围符合任务预期，且没有构建产物、临时文件或敏感文件；
2. 逐文件审查 `git diff`（必要时同时审查 staged diff），确认没有无关修改；
3. 根据 `AI工作流规范.md` 和适用的语言规则运行或确认验证；无法运行时记录原因和替代验证；
4. 按文件或逻辑分组暂存，避免无差别暂存未审查文件；
5. 确认提交信息、关联任务和文档结论与实际内容一致。

删除、批量改名和迁移按 `工程总纲.md` 确认范围；有兼容性或恢复风险时在交付中说明。

## PR / MR 门禁

合入受保护分支必须通过 PR/MR，且满足：

- 标题符合 Commit 格式，描述说明动机、变更、验证、兼容性/回滚影响以及关联 ADR（如有）；
- 所有仓库配置的必需 CI 检查通过；禁止绕过、关闭或忽略失败检查；
- C++ 项目的格式化、静态分析、编译与 Debug Sanitizer 要求以 `C++构建与依赖规范.md` 和 CI 配置为准，测试要求以 `测试规范.md` 为准；
- 变更由仓库分支保护或 CODEOWNERS 要求的人员审查；公共接口、并发、安全、性能关键路径、数据迁移和 CI 配置应由具备相应领域权限的审查者参与；
- 多人仓库不得以作者自审替代要求的独立审查；紧急例外须符合组织流程并留审计记录。
- 单人仓库且分支保护允许时，作者可自行合并，但须记录自审范围、验证与剩余风险；“作者可合并”不等于授权 AI 自动合并。

“CI 全绿”只代表已配置检查通过，不替代对变更范围、风险和测试有效性的人工审查。合并时机由用户决定：AI 不得自行合并，必须在用户明确同意后执行。

## GitHub Actions 与 CI 配置

`.github/workflows/*.yml`、复用工作流、执行脚本和发布流水线默认按 L 级评估，分级细则见 `AI工作流规范.md`；提交类型使用 `流水线`，Conventional Commits 仓库使用其对应 `ci` 类型。

- Sanitizer 是否运行、运行哪些组合及其构建参数由 `C++构建与依赖规范.md` 和实际工作流定义；`Git工作流规范.md` 只要求 PR 不得绕过对应必需检查。
- 工作流默认使用最小化 `permissions`；仅为必要 job 或 step 提升权限，禁止默认写权限。
- 第三方 Action 固定到经核实的完整 commit SHA，并以注释标明版本；升级时核对来源与变更。首次接入暂用版本标签时，须明确例外和完成固定的条件。
- 不在 workflow、日志、缓存键或命令行中输出 secrets、token 或私有配置；仅在确有需要的 job 注入最小范围的 secret。
- 来自 fork 或不可信 PR 的代码不得在可访问 secrets 或写权限的上下文执行。使用 `pull_request_target`、`workflow_run`、自托管 runner 或发布凭据时，必须单独评估权限边界并由相应负责人审查。
- 修改工作流后，至少检查 YAML 语法、触发条件、权限、依赖 Action 版本和失败路径；能够安全触发时，在隔离分支或 PR 上验证对应 job。

具体的 GitHub Actions YAML 是项目实现，不在本规则中重复；项目专属 CI 要求应随工作流存放并在仓库规则中登记。

## 保存点与异常处理

未完成工作默认不提交。确需跨会话保存时，只有在用户同意、位于个人功能/修复分支且不会推送或合入时，才可创建 `wip` 保存点；恢复后应整理为可审查的正式提交。

紧急修复可以走组织定义的紧急变更流程，但不得跳过风险说明、最小验证和事后审查。任何例外均应在 PR/MR 或任务记录中说明原因、批准依据和补救措施。
