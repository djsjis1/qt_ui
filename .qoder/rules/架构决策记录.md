# 架构决策记录规范

> 本文件覆盖：ADR 的触发条件、目录与索引、状态机、最小模板与维护方式。
> 给谁用：变更涉及长期架构取舍、第三方依赖、协议、存储、兼容性，或需创建/替代/查阅 ADR 时加载。

## 定位与边界

ADR 是长期设计取舍及其理由的权威记录。它解释“为什么”，不替代当前态文档的“现在是什么”。决策落地时必须同步更新相应的当前态文档。

ADR 仅记录存在真实备选项、长期影响或显著代价的决策。局部 bug 修复、常规补丁或可随时逆转的重构不需要 ADR。

---

## 触发与不触发条件

通常需要 ADR 的场景：

- 引入、替换或长期锁定第三方库、平台或运行时；
- 改变架构边界、依赖方向、通信协议、数据存储或安全模型；
- API/ABI、兼容性、可用性、性能关键路径之间存在长期取舍；
- 多个合理方案均可行，且选择将影响后续模块、团队或发布。

默认不创建 ADR 的场景：

- 既有 ADR、项目标准或已批准方案已完整覆盖本次实现；
- 纯局部实现、格式化、测试补充、常规依赖补丁或无行为重构；
- 没有真实备选项，或选择可轻易逆转且没有长期影响。

AI 在 Step 3 评估触发条件，先查找既有 ADR。用户要求保留待决方案时可创建“提议”ADR，仅当用户已选择或项目规则授权时才标为“已采纳”。

## 目录、索引与关联

```text
docs/adr/
├── README.md                    # ADR 索引
├── ADR-000-template.md           # 可选模板
└── ADR-001-简短描述.md
```

`docs/adr/README.md` 是 ADR 导航索引，至少包含编号、日期、标题、状态和替代关系。新建、采纳、拒绝、替代、废弃 ADR 时在同一变更中更新索引；项目摘要存在且导航受影响时，按 `文档规范.md` 更新稳定结论，不为 ADR 自动创建摘要。

提交或 PR 涉及 ADR 时，按 `Git工作流规范.md` 在提交描述或 PR 正文中注明 `ADR-XXX`。

## 状态与变更规则

| 状态 | 含义 |
| --- | --- |
| 提议 | 方案待决，尚未获得采纳 |
| 已采纳 | 已批准并作为实施依据 |
| 已拒绝 | 已评估但未采用，保留理由 |
| 已替代 | 被新的 ADR 明确替换 |
| 已废弃 | 不再适用，但未由单一新 ADR 直接替代 |

已采纳、已拒绝、已替代和已废弃 ADR 的决策内容不得被静默改写。发现事实错误可追加“勘误”章节；决策改变时创建新 ADR，并在新旧 ADR 及索引中双向关联。提议状态可以在决策前更新，但需保留关键方案和变更原因。提议转为已采纳时，采纳依据必须明确指向当前 ADR 编号及当前决策版本；项目规则授权须列出规则路径与授权范围。

## 最小模板

```markdown
# ADR-001：决策标题

- 状态：提议 / 已采纳 / 已拒绝 / 已替代 / 已废弃
- 日期：YYYY-MM-DD
- 替代/被替代：ADR-XXX（如适用）
- 决策版本：YYYY-MM-DD / 版本标识
- 采纳依据：批准记录链接或编号（提议状态填“无”；单人项目填“本人决策 YYYY-MM-DD”，无需另列批准人）

## 背景与问题

## 约束与决策标准

## 备选方案

### 方案 A
- 优点：
- 缺点与风险：

### 方案 B
- 优点：
- 缺点与风险：

## 决策与理由

## 后果与实施影响
- 需要更新的当前态文档：
- 兼容性、迁移、回滚和验证：
```

只有确实没有可行备选项时，说明原因；不得为凑模板虚构方案。

单人项目不需要外部审批人，但采纳仍必须留下日期依据；不得因为“没有别人可批”就把 ADR 长期停在提议状态或直接标为已采纳而不留依据。

## AI 维护与跨会话上下文

在已获授权的实施任务中维护相关 ADR 和索引；只读分析不创建、采纳或修改 ADR。开始涉及既有架构的工作时，先读取相关决策与当前态文档。摘要的创建与更新条件只在 `文档规范.md` 定义。

## 禁止行为

- 为每个 L 级变更或每个设计模式机械创建 ADR；
- 删除 ADR、复用编号或覆盖已采纳决策的历史；
- 仅更新 ADR 而不更新受其影响的当前态架构/API/模块文档；
- 在没有用户选择、批准记录或明确授权时宣称决策已采纳。
